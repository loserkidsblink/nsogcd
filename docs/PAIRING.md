# How Pairing Actually Works

This describes first pairing on the Bumble backend. Run `sudo nsogcd pair --wait`, then hold Sync until the LEDs sweep. After the controller is saved, an ordinary button press triggers host-targeted reconnect; the daemon skips the pairing and LTK setup steps below on that path.

## The User Experience

1. Controller is off / disconnected
2. With the explicit pairing window open, you hold the small Sync button by USB-C
3. Player LEDs do a chase pattern (~7 seconds)
4. ~3 seconds in, daemon has paired the controller and created a virtual gamepad
5. Steam, Dolphin, RetroArch — anything reading `/dev/input/event*` now sees a "Nintendo GameCube Controller"

## The 16-Step Technical Reality

### Step 1. HCI Takeover
Daemon boots. The service temporarily masks and stops `bluetooth.service`. Bumble grabs the available HCI adapter via `hci-socket:0`.

**Why bluetoothd has to die**: BlueZ holds an exclusive HCI session through its management interface. Two userspace BLE stacks cannot share one HCI device. This is the "BT headphones disconnect" trade-off.

### Step 2. LE Scan Setup
Daemon configures the radio for LE scan: passive mode, standard interval/window, accept-all filter policy.

### Step 3. Wait for an accepted advertisement
The daemon scans continuously. For first pairing, it accepts the NSO GameCube advertisement with a zero target address only while an explicit pairing window is open. For a saved controller, an ordinary button wakes it and the daemon accepts its advertisement only when it targets this host address. Holding Sync outside a pairing window is ignored.

### Step 4. Initiate Connection
Daemon issues LE_Create_Connection to the controller BD_ADDR with these parameters:
- Connection interval: 7.5-15ms (low latency for gaming)
- Latency: 0
- Supervision timeout: ~5 seconds

### Step 5. Standard SMP Pairing Attempt (First Pairing Only; Expected to Fail)
Bumble tries standard SMP pairing with our PairingDelegate config:
- Legacy SMP, sc=False, mitm=False, bonding=True
- IO capability: NoInputNoOutput
- Initiator key distribution: DISTRIBUTE_IDENTITY_KEY (0x02)
- Responder key distribution: DISTRIBUTE_ENCRYPTION_KEY (0x01)

The controller responds with Pairing Request demanding Bonding + MITM + SC + CT2 (auth requirement byte 0x2d). Bumble cannot satisfy MITM with NoInputNoOutput, so SMP fails with Pairing Not Supported (0x05).

**This is normal. Ignore the error. Continue.**

### Step 6. MTU Exchange
The controller input reports are 63 bytes. BLE default MTU is 23 bytes (would fragment notifications). Daemon issues ATT_MTU_Exchange requesting 512, controller agrees on 247 or 185.

**If skipped**: input notifications silently truncated. Daemon would receive partial reports.

### Step 7. GATT Service Discovery
Daemon walks the GATT tree, discovers two custom services. Caches handle numbers for the command write/response chars.

### Step 8. Enable SW2 Service
Daemon writes `0x01 0x00` to handle `0x0005`. Activates the proprietary protocol on the controller side. Without this, all subsequent commands are silently dropped.

### Step 9. Subscribe to Command Response Channel
Daemon writes `0x01 0x00` to handle `0x001B` (command response CCCD). Now we can receive ack/response notifications.

### Step 10. Read Device Info
Daemon reads SPI offset `0x00013000` (64 bytes). Returns ASCII serial number, USB VID/PID, firmware version, controller color codes.

### Step 11. Proprietary 4-Step Pairing Handshake (First Pairing Only)
The magic Nintendo demands instead of standard SMP:
- STEP1: cmd=0x15 sub=0x01 with the Legion BD_ADDR. Controller stores this as new peer.
- STEP2: cmd=0x15 sub=0x04 with fixed nonce EA BD 47 13 89 35 42 C6 79 EE 07 F2 53 2C 6C 31
- STEP3: cmd=0x15 sub=0x02 with fixed nonce 40 B0 8A 5F CD 1F 9B 41 12 5C AC C6 3F 38 A0 73
- STEP4: cmd=0x15 sub=0x03 (empty payload). Controller acknowledges, handshake complete.

The fixed nonces are not session-derived. They are a hardcoded shared value that both Nintendo console and controller know.

### Step 12. Read LTK from SPI (First Pairing Only)
Daemon reads SPI offset `0x001fa000` length 0x40. Extracts:
- Status byte at 0x1fa000 (should be 0x02)
- EDIV at 0x1fa00e (typically 0)
- RAND at 0x1fa010 (typically 8 zeros)
- LTK at 0x1fa01a (16 bytes)

The LTK was generated by the controller as part of step 11.

### Step 13. HCI LE Enable Encryption (First Pairing Only)
Daemon issues HCI_LE_Enable_Encryption_Command with the extracted LTK + EDIV + RAND. Tries three combinations: extracted, zeros-with-LTK, zeros-with-reversed-LTK. When one succeeds, BLE link is encrypted.

### Step 14. Set Player LED
Daemon writes cmd=0x09 sub=0x07 with player LED mask 0x01. Controller LED 1 lights up solid.

### Step 15. Enable Input Notifications
Daemon writes `0x01 0x00` to handle `0x000B` (input CCCD). Subscribes to handle `0x000E` notifications. Disables command response CCCD so input does not collide with cmd response on the same channel.

### Step 16. Create uinput Device
Daemon opens `/dev/uinput` and creates a virtual gamepad with name "Nintendo GameCube Controller", VID 0x057E, PID 0x2073, all buttons + 4 sticks + 2 triggers + D-Pad. `/dev/input/eventXX` now exists.

These steps describe the initial enrollment path; button-wake reconnect skips the first-pairing operations.
